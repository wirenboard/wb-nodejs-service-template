# Как устроен сервис WB и как он пакетируется

Подробные пояснения и рекомендации: как писать сервис, откуда берётся версия пакета,
как устроены тесты и сборка deb, FAQ по пакетированию и проверка на контроллере.
Этот текст перенесён из README шаблона, чтобы на главной странице остался только шаблон.

---

## Рекомендации и пояснения

### Требования к шаблону

Шаблон не должен быть пустым каркасом: он показывает приёмы, и каждый приём обязан быть
показан на живом коде, а не в комментарии. Минимальный набор:

 - **хотя бы одна внешняя зависимость.** Иначе не видно главного — как зависимости попадают
   в пакет: `npm ci` на сборке, чистка дерева, проверка инварианта `Architecture: all`, SBOM,
   фиксация версий в lock-файле. Без зависимости весь этот конвейер приходится описывать
   словами, и первый же человек соберёт его по-своему.
 - **подключение к MQTT.** Сервис Wiren Board без брокера почти не бывает.
 - **подписка.** Реакция на входящее сообщение — половина работы типового сервиса,
   и она должна быть в примере, а не в документации.
 - **публикация.** Виртуальное устройство с контролами и метаданными по конвенции:
   типы, единицы, `readonly`, порядок, переводы.
 - **минимальная полезная функция.** Такая, чтобы README начинался со слов «сервис делает
   то-то», а не «сервис ничего не делает». Без неё нельзя написать внятный README,
   а значит и структура документа получится кривой.
 - **динамичность.** Значения обязаны заметно меняться от обновления к обновлению.
   Статика вроде свободного места на диске выглядит в интерфейсе одинаково и когда сервис
   работает, и когда он завис, — по такому примеру не видно, что он вообще живой. Поэтому
   в итоге взяли скорость трафика: она шевелится сама, без участия пользователя.
 - **интерактивность.** Хотя бы один записываемый контрол: кнопка или переключатель.
   Во-первых, это единственный способ показать в примере обработку входящих сообщений.
   Во-вторых, нажатие должно давать **видимый результат** — если после нажатия на экране
   ничего не меняется, пользователь не понимает, сработало ли, и пример получается мёртвым.

### Что делает сервис

Читает конфиг из `/etc` или из пути после `-c`, подключается к MQTT-брокеру на localhost
и публикует виртуальное устройство `wb-nodejs-service-template` с четырьмя контролами:
скорость приёма на интерфейсе из конфига, её максимум с момента старта, время работы
сервиса и кнопка сброса максимума. Значения обновляются по таймеру с периодом
`update_interval` из конфига.

Скорость считается по `/proc/net/dev`: берётся счётчик принятых байт нужного интерфейса
и делится разница между двумя замерами на прошедшее время. Счётчик может уехать назад
(перезагрузка, переполнение на 32-битных ядрах), поэтому отрицательная разница считается
нулём, а не отрицательным трафиком.

Интерфейс, которого нет в системе, помечается ошибкой в `meta/error` своего контрола,
остальные контролы продолжают обновляться — сервис из-за опечатки в конфиге не падает.

При подключении ставится Last Will, чтобы брокер сам пометил аварийную смерть сервиса.
По `SIGTERM` и `SIGINT` сервис останавливается штатно и затирает за собой retained-топики,
иначе устройство навсегда зависнет в интерфейсе. При отсутствующем, битом или
бессмысленном конфиге выходит с кодом 6, на который настроен systemd-юнит.
Умеет `--version`.

### Режимов работы нет, и это нормально

В питоновском шаблоне в конфиге лежит `mode` с выбором между `one_thread` и `threaded`.
Эта развилка существует из-за того, что `paho-mqtt` синхронный: его цикл надо где-то крутить,
либо в основном потоке через `loop_forever()`, и тогда своей работы делать негде, либо
в отдельном потоке, и тогда появляются очередь и второй поток.

В Node такой развилки нет. `mqtt.js` событийный, обработчик входящих сообщений и таймер
живут в одном цикле событий одновременно. Поэтому оба питоновских режима покрываются сразу:
реакция на входящие — это `client.on('message', ...)`, своя работа по расписанию — обычный
`setInterval`, как сделано здесь для пересчёта скорости.

Если ищете `mode` в конфиге — его нет и не будет. Единственный настоящий аналог потоков
в Node это `worker_threads`, и он нужен только для тяжёлых расчётов, которые иначе
заблокируют цикл событий. Это решение при проектировании сервиса, а не параметр конфига.

### Сервис

 - **MQTT-клиент** — пакет [mqtt](https://github.com/mqttjs/MQTT.js) (mqtt.js). Он событийный:
   подписки и таймеры живут в одном цикле событий, отдельные потоки не нужны. Переподключение
   клиент делает сам, обработчик `connect` вызывается и после разрыва — там же и перепубликация
   устройства. Обработчик `close` нужен, чтобы отличить потерю живого соединения от неудачной
   попытки подключения: на старте без брокера `close` сыплется каждую секунду, и сообщать об
   этом как о разрыве не надо.

 - **Перехват сигналов** — `process.on(signal, handler)` для `SIGTERM` (остановка через
   `systemctl stop`), `SIGINT` (Ctrl-C в консоли) и `SIGHUP` (закрытие терминала). Node передаёт
   имя сигнала в обработчик, поэтому одного обработчика хватает на все три. Выход делается явно:
   после затирания топиков клиент закрывается и в его колбэке вызывается `process.exit(0)`.
   Полагаться на то, что цикл событий опустеет сам, не стоит — в нём может остаться чужой
   таймер или открытый дескриптор, и сервис повиснет на остановке до `SIGKILL` от systemd.

   **Остановка обязана работать и без брокера.** Это неочевидное место: по умолчанию mqtt.js
   складывает публикации QoS 0 в свою внутреннюю очередь, пока соединения нет, и колбэк такой
   публикации не вызывается до переподключения. Значит затирание топиков не завершится никогда,
   а вместе с ним и остановка: `systemctl stop` будет ждать `TimeoutStopSec` (по умолчанию 90
   секунд) и добьёт сервис `SIGKILL`. На контроллере это видно при каждом рестарте брокера.
   Лечится двумя строчками: `queueQoSZero: false` в опциях подключения, чтобы публикация
   сразу сообщала об ошибке вместо молчания, и `setTimeout(exitSuccess, …).unref()` в
   обработчике сигнала как страховка на будущее. Очередь при этом заодно перестаёт расти:
   значения, измеренные без брокера, всё равно не нужны, после переподключения сервис
   публикует устройство заново.

 - **Виртуальные устройства снимает сам сервис.** Свои устройства сервис публикует с `retain`,
   поэтому после остановки они остаются на брокере и продолжают висеть в интерфейсе. Убрать их
   можно единственным способом, отправив в те же топики пустое значение, и сделать это может
   только сам сервис.

   Снятие ставится на штатный путь остановки: обработчик сигнала снимает таймер, затирает топики
   устройства и только после этого отключается от брокера. Писать это в `finally` нельзя, иначе
   оно сработает и при падении с необработанным исключением.

   При аварийной смерти устройства должны остаться на месте и показывать ошибку, чтобы поломка
   была видна. Для этого сервис до подключения регистрирует Last Will с записью ошибки в
   `meta/error`, у самого устройства или у любого его контрола. Брокер отправит её сам, когда
   потеряет клиента. При штатном отключении Last Will не срабатывает, так брокер и отличает
   падение от нормальной остановки.

   **В топике ошибки лежат флаги, а не текст.** По
   [конвенциям](https://github.com/wirenboard/conventions) это комбинация из `r` (не удалось
   прочитать), `w` (не удалось записать) и `p` (пропущен период опроса). Писать туда фразу
   вроде `service died` нельзя: читатель, который разбирает флаги, получит мусор. Для умершего
   сервиса ближе всего `r` — опубликованные значения остаются последними достоверными.

 - **Устройство объявляется один раз.** Заголовок и все контролы с метаданными лежат в константе
   `DEVICE`, а публикация, затирание при остановке и сборка топиков выводятся из неё. Добавление
   контрола — одна запись в объявлении, и больше нигде. Имена контролов тоже объявлены однажды,
   в `CONTROL`, и подставляются в `DEVICE` вычисляемыми ключами.

   Публикация устройства заодно гасит ошибки: и у самого устройства, и у каждого контрола.
   Ошибка лежит на брокере с `retain`, поэтому оставленная прошлым запуском она висела бы
   на контроле вечно. А дальше ошибка пишется только при изменении: сервис, который каждую
   секунду публикует пустой `meta/error`, засоряет шину всем, кто слушает устройство.

 - **Запуск.** Весь код лежит в `src/`, точка входа — функция `main(argv)`, которая **возвращает**
   код возврата, а не завершает процесс. Запуск происходит только когда файл вызван напрямую, под
   охранником `import.meta.url === pathToFileURL(process.argv[1]).href` — это аналог питоновского
   `if __name__ == "__main__"`. Благодаря ему импорт модуля в тестах ничего не запускает.

   Обёртку в `bin/` делаем **всегда**, даже если сервису не нужен CLI. Причин три. Единообразие —
   любой сервис WB запускается одинаково и его точка входа лежит в предсказуемом месте. Готовое
   место под `--version`, которую мы добавляем каждому сервису. И запас на будущее — если из
   сервиса понадобится сделать настоящую утилиту с флагами, пакетирование переделывать не придётся.

   Сама обёртка — на шелле, а не на JavaScript. У питона импорт по имени пакета работает откуда
   угодно, потому что пакет лежит в общем `dist-packages`. У Node такого общего пути нет: импорт
   из `/usr/bin` не найдёт код в `/usr/lib`, и путь пришлось бы зашивать в JS абсолютной строкой.
   Строка `exec` в шелле делает то же самое явно, и в неё потом легко добавить флаги ноды.

 - **`--version`.** Каждый сервис умеет печатать свою версию. Флаг разбирается там же, где
   остальные аргументы, и обрабатывается до чтения конфига — значит версию можно спросить и у
   сервиса с испорченным конфигом. Делаем именно `--version` без короткой формы, потому что `-v`
   в наших утилитах часто занят под verbose.

 - **Уровень журнала.** В конфиге лежит `log_level` со значениями `error`, `info` и `debug`.
   Метод `log(level, message)` печатает сообщение, только если настроенный уровень достаточно
   подробный. Параметр необязательный, по умолчанию `info`: сервис, который никто не отлаживает,
   должен быть тихим. Обратите внимание, что в части сервисов WB вместо уровня до сих пор стоит
   булев `debug` — при переносе кода это стоит учитывать.

### Версия пакета

Источник версии один — `debian/changelog`. Дальше она расходится так.

1. В коде лежит константа `VERSION` со значением-заглушкой `0.0.0-dev`. На сборке
   `override_dh_install` подменяет её в **установленной копии** файла, то есть в
   `debian/<пакет>/usr/lib/<пакет>/main.js`. Исходник при этом не меняется: сборка не должна
   оставлять после себя правок в рабочем дереве.
2. Всё от первой тильды отрезается, в коде остаётся только релизная часть. На сборке ветки
   или PR Jenkins дописывает суффикс, и версия выглядит как `1.0.0~exp~PR+1~1~g34c85c7`;
   npm такую строку не принимает, `npm sbom` падает с `EINVALIDTAGNAME`. Режем по тильде,
   ровно как `parse_changelog_version` в питоновском шаблоне. Полная deb-версия всегда
   видна в `dpkg -l` и в диагностическом архиве.
3. `npm sbom` отказывается работать без версии в `package.json`, поэтому на время генерации
   SBOM версия проставляется туда же и сразу возвращается к `0.0.0`.
4. Формат проверяет сама сборка: `npm pkg set version` не принимает строку, которую npm
   не сможет использовать. В тестах формат проверять бессмысленно — они идут раньше, чем
   версия подставляется, и видят только заглушку.

В `package.json` поле `engines` задаёт нижнюю границу, которую требует код, а `.nvmrc` —
версию, которая стоит на контроллерах. Они не обязаны совпадать: первое про совместимость,
второе про окружение.

### Как именуем тесты

Имя теста в Node-шаблоне — это формулировка одноимённого теста из питоновского шаблона,
записанная словами, без `test_` и подчёркиваний. Смысл простой: два набора тестов должны
читаться как один список на двух языках, тогда видно, чего где не хватает.

```
питон:  def test_config_path_defaults_to_the_packaged_one_and_can_be_overridden()
node:   test('config path defaults to the packaged one and can be overridden', ...)

питон:  def test_an_unusable_config_returns_config_error()
node:   test('an unusable config returns config error', ...)
```

Порядок в файле тоже общий: сначала про конфиг и аргументы, потом про работу сервиса,
в конце про версию.

Чего выравнивать **не** надо — форму. pytest ждёт `test_*.py` и функции, `node --test` — `*.test.js`
и строки, временные файлы делаются через `tmp_path` и через `mkdtempSync`, перехват вывода —
через `capsys` и через `t.mock.method`. Выравнивание по форме даёт неидиоматичный код в обоих
шаблонах, выравнивание по словам не стоит ничего.

Если теста нет в парном шаблоне — это не повод его не писать, это повод завести задачу
и добавить его туда тоже.

### Тесты

Тесты запускает встроенный раннер Node — `node --test` без аргументов. Он сам находит файлы
`*.test.js` и не требует ни конфига, ни зависимостей: раннер входит в ноду начиная с 20-й версии.
Поэтому в `Build-Depends` для тестов ничего добавлять не нужно, а `devDependencies` у шаблона нет
вовсе.

На сборке тесты запускает `override_dh_auto_test` и уважает `nocheck` в `DEB_BUILD_OPTIONS`,
как принято в Debian. Локально команда та же самая, из корня проекта.

**Каталог аргументом не передаём.** `node --test tests/` на некоторых версиях ноды пытается
загрузить `tests` как модуль и падает с `Cannot find module`. Голый `node --test` работает везде.

**Модуль обязан быть безопасным для импорта.** Тесты импортируют `src/main.js` и зовут его
функции напрямую, поэтому на уровне модуля не должно происходить ничего: ни чтения конфига, ни
подключения к брокеру, ни таймеров. Запуск живёт под охранником в конце файла. По той же причине
`main()` возвращает код возврата, а не вызывает `process.exit` — иначе первый же тест убьёт
раннер.

**Брокер для тестов не нужен.** Обработчики — это методы класса, так что в тесте создаётся
экземпляр, в его поле `client` кладётся подставной объект с одним методом `publish`, который
просто собирает сообщения, и дальше обработчик дёргается напрямую.

**Один тест на поведение, а не на случай.** Пять способов испортить конфиг — это один тест с
пятью проверками, а не пять тестов: ветка кода там одна. Имя проверяемого файла передаётся
третьим аргументом `assert`, чтобы при падении было видно, какой именно случай сломался.

### Линтер и автодополнение

Линтера в шаблоне пока нет. В организации есть готовый flat config —
[wirenboard/eslint](https://github.com/wirenboard/eslint), его стоит подключить, когда у сервиса
появится заметный объём кода.

Файл автодополнения для bash кладётся в `completions/<имя-утилиты>.bash`, а в
`debian/<пакет>.install` добавляется строка с путём `/usr/share/bash-completion/completions`.
В шаблоне такого файла нет намеренно: у CLI всего два флага, дополнять в них нечего.

### Единицы и флаги ошибок

Типы контролов, единицы измерения и значения в топиках ошибок заданы
[конвенциями](https://github.com/wirenboard/conventions) — это общий язык для всех сервисов
WB и для веб-интерфейса, который по единице подбирает перевод.

Единицы скорости передачи данных в конвенциях нет вовсе, поэтому `KiB/s` в шаблоне — это
осознанное отклонение: homeui покажет её как есть, без перевода. Если такое не устраивает,
единицу убирают из метаданных и выносят в название контрола. Придумывать свои единицы вместо
тех, что в списке, не нужно: перевода у них всё равно не будет, а конвенция размоется.

В топиках ошибок (`meta/error` у устройства и у контрола) лежит комбинация флагов `r`, `w`
и `p`, а не текст. Это касается и Last Will, см. раздел «Сервис».

### Комментарии и JSDoc

**Комментарии и сообщения в журнал пишутся по-английски.** Код уходит в публичные репозитории, а
журнал попадает в диагностические архивы, где русский текст мешает читать и грепать.

**Комментарий объясняет «почему», а не «что».** Пересказ имени функции читать только мешает.
Хороший комментарий отвечает на вопрос, который возникнет у читателя: почему счётчик
трафика может уехать назад; почему затирание топиков не в `finally`;
почему обработчики привязываются в конструкторе.

**JSDoc пишем там, где он добавляет контракт**, которого не видно из имени и подписи: что
возвращает функция, когда возвращает `null`, что бросает. У коротких обработчиков событий его
нет — там всё видно из имени.

## Пакетирование

### Как раскладываются файлы Node-сервиса и почему так

Приложение ставится в `/usr/lib/<пакет>`, рядом с ним вендоренный `node_modules`,
точка входа - в `/usr/bin`. Список файлов задаётся в `debian/<пакет>.install`,
и там работают маски, так что строка `src/*` покрывает все модули сразу: добавили
файл в `src/` - упаковку править не надо. Внимание на звёздочку, `src` без неё
положит саму папку и получится `/usr/lib/<пакет>/src/main.js`.

Два других пути рассмотрели и отвергли:

 - **`pkg-js-tools` (`dh-sequence-nodejs`)** - штатная автоматика Debian. Читает
   `package.json`, сама раскладывает файлы по полю `files`, сама делает симлинки
   в `/usr/bin` по полю `bin`. Не подошла, потому что кладёт всё в `/usr/share/nodejs`
   и рассчитана на дебиановскую модель, где зависимости приезжают системными пакетами
   `node-*`, а `node_modules` собирается из них симлинками. У нас таких пакетов нет
   и не будет: нужных нам библиотек в Debian никто не паковал, поэтому зависимости вендорятся.
   Подключив этот инструмент, мы получили бы помощника, который борется с нашей схемой.

 - **`npm install -g --prefix debian/<пакет>/usr`** - npm сам разложит приложение
   в `/usr/lib/node_modules/<имя>` и сам сделает симлинк в `/usr/bin`. Отвергли:
   путь жёстко задаёт npm, поведение при обновлениях надо проверять отдельно,
   а экономия - три строки в `debian/install`.

Итог: обычный `debian/install` с масками. Явно, предсказуемо и ровно так же сделано
в `wb-node-red`, единственном Node-пакете WB, который ставится на контроллер нативно.

_Исходная система_ - где происходит сборка deb-пакета. В терминологии debian - **build**-система
_Целевая система_ - куда устанавливается пакет. В терминологии debian - **host**-система

Для сборки deb-пакетов в Wiren Board используется кросс-компиляция. Это значит, что сборка
будет происходить на машине с архитектурой, отличной от той, на которой всё будет запускаться, и нужно подсказать сборщику, как правильно разрешать зависимости.

 - **Собрать пакет вручную** и посмотреть что получается можно внутри [devcontainer-a](https://docs.google.com/document/d/19gT4BH6MO-XXyqqzTOoz-jhY0ITbeGKDOZ8FbV_J1tc/edit?tab=t.0) командой
    ```
    dpkg-buildpackage -rfakeroot -us -uc
    ```
    Директория debian в проекте (исходная система) будет содержать структуру директорий относительно корня целевой системы. Перед сборкой не забыть установить build-depends.

 - **/debian/control для Node**

    В `Build-Depends` идут `debhelper-compat` и сама нода нужной версии. **npm туда писать не надо**:
    он приезжает вместе с нодой, а дебиановский пакет `npm` с ней конфликтует.
    ```
    Source: wb-my-service
    ...
    Build-Depends: debhelper-compat (= 13),
                   nodejs (>= 22.13)
    ```
    Для binary пакета
    ```
    Package: wb-my-service
    Architecture: all
    Depends: ${misc:Depends},
             nodejs (>= 22.13)
    ```
    `Architecture: all` (не путать с `Architecture: any`) означает платформонезависимый пакет.
    Для Node это работает ровно до тех пор, пока в дереве зависимостей нет нативных модулей,
    поэтому `debian/rules` проверяет это инвариантом: сборка падает, если в `node_modules`
    нашёлся хоть один `*.node`.

 - **Jenkinsfile**

   В шаблоне вызов пайплайна закомментирован намеренно. Иначе Jenkins собирал бы сам шаблон и публиковал его в релизный фид, где шаблону не место. В настоящем пакете эти строки надо раскомментировать.
   ```groovy
   buildDebArchAll defaultRunLintian: true
   ```
   `defaultRunLintian` добавляет стадию после сборки, на которой готовый deb проверяет
   дебиановский линтер `lintian` с профилем WB из
   [codestyle](https://github.com/wirenboard/codestyle). Он смотрит на упаковку, а не на код,
   и валит стадию на замечаниях уровня error. По умолчанию в хелпере выключен, поэтому
   включаем явно: проверка от языка не зависит и нужна всем.

   Остальные флаги `buildDebArchAll` — про питоновские проверки (`defaultRunPythonChecks`
   для `black`, `isort` и `pylint`, `defaultAngryPylint` для фатальности их ошибок), для Node
   аналога пока нет. Когда подключим [eslint](https://github.com/wirenboard/eslint), стадию
   проверок кода надо будет добавить сюда же.

 - **Резервное копирование конфигов**

   Сервис [wb-configs-early](https://github.com/wirenboard/wb-configs/blob/master/debian/wb-configs.wb-configs-early.service) умеет делать резервное копирование файлов перед началом работы системы и перед выключением. Он перемещает сам файл конфига в раздел, который не сбрасывается при установке обновлений, а сам конфиг в исходном расположении `/etc/` заменяет на симлинк. Для этого нужно в папку `/etc/wb-configs.d` положить скрипт, который вызовет `wb_move` для всех нужных конфигов (в данном примере это `10wb-python-service-template`).
   

## FAQ по сборке и пакетированию для продвинутых

 - **Почему all-пакеты не собираются в sbuild с `--host=armhf`?**

   Альтернативная формулировка - почему all-пакеты нельзя было раньше собрать через `wbdev cdeb`.

   Во-первых, потому что в Debian обычно делят сборку all-пакетов и кросс-компиляцию,
   вот ([пруф](https://wiki.debian.org/CrossBuildPackagingGuidelines)).

   Во-вторых, это могло бы заработать, если бы мейнтейнеры библиотек в Debian озадачивались
   добавлением `Multi-Arch: foreign` в свои пакеты. На ноябрь 2022 этой пометки не было
   как минимум в тех, что мы тогда часто использовали.

   В итоге оказалось проще пойти каноничным путём и собирать `all` и `any` отдельно.

 - **Для чего при сборке cdeb запускаются и `--arch-all`, и `--arch-any`?**

   Раньше для сборки пакетов отдельно использовались `wbdev cdeb` (для `any`) и
   `wbdev ndeb` (для `all`). Это было очень актуально во времена `wheezy`, когда
   не было ещё multiarch, и пакеты для Wiren Board приходилось собирать в chroot
   с qemu. Тогда для экономии времени сборки (qemu медленный) сделали отдельно
   команду `ndeb`, которой собирали `all`-пакеты прямо в Docker-окружении.

   Потом мы перешли на sbuild, и разница между `cdeb` и `ndeb` стала размываться,
   потому что для обеих команд уже использовалось sbuild-окружение, только с
   разным аргументом `--host`.

   *Так получилось*, что при переходе на релизную систему, когда для сборки
   стало нужно указывать, для какой платформы происходит сборка (wb5/wb6/wb7),
   добавление наших репозиториев (`http://deb.wirenboard.com/wbX/<deb-release>`)
   делалось только в `cdeb`. Для `ndeb` появился репозиторий `dev-tools`, который
   нужен скорее для сборки пакетов, нужных нам на производстве и для CI.

   Пока наши all-пакеты не зависели друг от друга при сборке, можно было продолжать
   пользоваться такой системой, выбирая в зависимости от типа пакета `cdeb` или `ndeb`.
   При разработке wb-device-manager нам понадобились all-зависимости из нашего репозитория.

   В этот момент @webconn решил, что пора объединять `cdeb` и `ndeb` - так получается
   меньше пайплайнов для CI и не надо дублировать код в devenv. Также меньше возможностей
   ошибиться при сборке - скрипты сами сделают всё, что нужно.

   `ndeb` с этого момента стал deprecated, о чём пишется WARNING.


## Перед контрибьютом

Перед тем как открывать PR, убедитесь, что:

1) Код проходит тесты (из корня проекта `node --test`);
2) Концы строк во всех файлах остаются `LF` (это обеспечивает `.gitattributes`);
3) Пакет успешно собирается и на выходе получается deb-файл;
4) Пакет проверен на реальном контроллере:
   - Устанавливается;
   - Сервис публикует своё устройство в MQTT;
   - Пакет сообщает свою версию по `--version`;
   - Сервис запускается сам после установки;
   - Сервис автоматически стартует после перезагрузки контроллера;
   - После остановки сервиса его устройство исчезает из веб-интерфейса;
   - Пакет удаляется.

### Проверка сборки на контроллере

Выполняется на самом Wiren Board (арх `all`, подойдёт любой).
Репозитории WB на контроллере должны быть настроены — из них тянется нода нужной версии.

```bash
# 1. Инструменты сборки (один раз на контроллер)
sudo apt update
sudo apt install -y debhelper devscripts equivs git

# 2. Копия из своей ветки
GIT_BRANCH_NAME="feature/branch-name"
git clone -b "${GIT_BRANCH_NAME}" --single-branch \
  https://github.com/wirenboard/wb-nodejs-service-template.git
cd wb-nodejs-service-template

# 3. Build-зависимости из debian/control и сборка пакета
sudo mk-build-deps -ir debian/control
dpkg-buildpackage -us -uc -b
```

Далее нужно проверить что пакета корректно собран и сервис поднимается сам

```bash
# 1. Установка собранного пакета
sudo apt install -y ../wb-nodejs-service-template_*.deb

# 2. Версия из debian/changelog
wb-nodejs-service-template --version

# 3. Проверка работы сервиса
systemctl is-enabled wb-nodejs-service-template   # ожидается: enabled
systemctl status wb-nodejs-service-template       # ожидается: active (running)

# 4. Устройство появилось в MQTT и в веб-интерфейсе
mosquitto_sub -v -t '/devices/wb-nodejs-service-template/#' -W 3

# 5. Проверка автозапуска после перезагрузки
sudo reboot
# после загрузки снова зайти по SSH и проверить, что сервис поднялся сам:
systemctl status wb-nodejs-service-template       # ожидается: active (running)

# 6. Удаление после проверки
sudo apt purge -y wb-nodejs-service-template
```

При успешной сборке `node --test` прогонит тесты из `tests/` (шаг сборки `dh_auto_test`),
а после установки сервис включится автоматически благодаря секции `[Install]` в юните.
После остановки сервиса его устройство должно исчезнуть из веб-интерфейса — это проверка того,
что затирание retained-топиков работает.
